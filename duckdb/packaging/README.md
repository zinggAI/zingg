# Packaging

`package.ps1` builds all Maven modules with tests skipped and assembles the worker, Python control plane, runtime manifest, notices, and SHA-256 inventory under `dist/zingg-duckdb-0.1.0`. On Unix, invoke the equivalent `./packaging/package.sh`, which provides a stable shell entry point to the cross-platform assembler. Production bundles must use `-CreateJre` to include the bundled Java 21 runtime; the packaged Python client rejects a distribution that contains the worker but lacks `runtime/java`.

The bundle layout is consumed directly by the Python client: the executable worker is under `worker/`, the Python package under `python/`, and an optional project-bundled JRE under `runtime/java/`. The client also retains a checkout fallback to `runtime-worker/target/` for local development.

The production distribution must add the selected signed Java 21 `jlink` runtime under `runtime/java/`. The manifest deliberately records Java as bundled and disables extension auto-installation.

Generate the local runtime with `./packaging/create-jre.ps1` from PowerShell or `./packaging/create-jre.sh` from a POSIX shell, using a Java 21 JDK. The selected JDK vendor, build, checksum, and security-update policy must be recorded in the release provenance before distribution.

The optional exact-contract bootstrap is `./packaging/prepare-zingg07-capsule.ps1` on Windows or `bash packaging/prepare-zingg07-capsule.sh` on Linux/WSL. Both check out commit `48cb157b4f35fcfa733e2e7f9699ea988e018738`, build `common/client` with `-Dzingg.version=0.7.0`, and use the shared Python canonicalizer plus the 93-signature inventory check. The Windows output defaults to `dist/zingg-common-client-0.7.0.jar` with `dist/zingg07-capsule-manifest.json`; POSIX outputs both under `dist/zingg07-capsule/`. Neither overwrites Maven's artifact cache. The expected canonical SHA-256 is `a289903fae2ed9ff3a0a3360fed3c80232d70fce848df27e2c6a6ee8406c4b5d`, reproduced locally on Windows and WSL. This is not release approval: hosted clean-runner reproduction, licensing, full provenance, and functional adapter coverage remain open.

For a signed release, run `./packaging/sign-package.ps1 -Bundle dist/zingg-duckdb-0.1.0 -CertificateThumbprint <thumbprint>` after packaging, then verify it with `./packaging/verify-package.ps1 -Bundle dist/zingg-duckdb-0.1.0 -RequireJre -RequireSignature`.

After assembly, run `./packaging/verify-package.ps1 -Bundle dist/zingg-duckdb-0.1.0 -RequireJre`. The verifier checks the SHA-256 inventory, SPDX 2.3 package/relationship integrity, exact/hash-verified runtime dependency legal-resource inventory, profile presence, embedded worker/JRE, and absence of Python cache directories; `package.ps1` invokes the same gate automatically. The runtime-worker Maven package phase stages the resolved runtime JARs under `runtime-worker/target/runtime-dependencies`; packaging copies every legal resource from those original JARs to `licenses/third-party/` with a `DEPENDENCY-NOTICES.json` index of source paths and SHA-256 hashes. This preserves original per-dependency files even when the shaded JAR reports duplicate META-INF resources. Both packaging paths also collect Maven's JSON dependency tree from every reactor module and inspect the shaded worker's embedded `pom.properties`. Coordinates found only in retained/relocated upstream Maven metadata are kept in the SBOM with a review comment instead of silently omitted. The current build surfaces `org.jctools:jctools-core:4.0.5` this way: Netty relocates JCTools classes into its own namespace while retaining their Maven metadata. Third-party license fields remain `NOASSERTION` unless supported by reviewed evidence; the legal-resource archive and structural SBOM validation are inventories, not license/security approvals. Separate legacy JARs and the optional vendor-specific JRE still require explicit release-artifact/license reconciliation.

Create a reproducible source capsule with `./packaging/create-source-archive.ps1 -Root . -Output dist/zingg-duckdb-source.zip`. The archive excludes Git metadata, build outputs, distributions, and Python caches, and contains `SOURCE-MANIFEST.json` with per-file SHA-256 hashes. The PowerShell and POSIX wrappers invoke one canonical ZIP writer with fixed entry root, schema, ordering, timestamps, modes, and stored payloads; identical source bytes therefore produce identical archive bytes across platforms. Verify it offline with `./packaging/verify-source-archive.ps1 -Archive dist/zingg-duckdb-source.zip` before publishing. The wrappers share a Python verifier that validates ZIP paths and member types without extracting untrusted archive contents, then checks exact inventory and streamed SHA-256 digests.

Bundle SHA-256 inventories are generated by `write_bundle_manifest.py` and checked by the shared `verify_bundle_inventory.py` implementation used by both `verify-package.ps1` and `verify-package.sh`. It requires an exact inventory and rejects unsafe paths, hash errors, unlisted files and external symlinks while supporting internal jlink symlinks. Both wrappers also use the same `verify_package.py` contract validator for required bundle files, duplicate-free compatibility/profile/release-policy JSON, source and worker-artifact provenance (including the actual worker JAR digest), Java 21 declarations, and Python-cache exclusion. `-RequireJre`/`true` additionally requires the host Java executable, verifies its Java 21 version text and checks the JDK legal/provenance inventory. This shared check prevents Windows and POSIX assemblers from silently accepting structurally different bundles.

`package.ps1` creates and verifies this source capsule automatically beside the binary bundle. The bundle also contains `config/compatibility-capsule.json`, which records the upstream profile, source/dependency provenance, notices, patches, and process-isolation boundary.

`generate-provenance.ps1` and `generate-provenance.sh` delegate to `generate_provenance.py`. For identical source/build inputs they emit byte-identical LF-normalized JSON containing root release files, each module POM and available dependency lock, and the worker artifact hash. The package verifier validates every declared source record's normalized relative path, uniqueness, and SHA-256 shape, requires the root source inventory, and checks both recorded worker hashes against the packaged worker JAR. When the sibling `zingg-duckdb-source.zip` exists, both verification wrappers also validate it without extraction and compare every provenance source record with its `SOURCE-MANIFEST.json`; a standalone bundle without the sibling archive still receives structural and worker-hash validation.

The hosted workflow has distinct evidence tiers. `compile` performs packaging tests and test-skipped Maven compilation on Linux amd64/arm64, macOS x86_64/arm64, and Windows x86_64. `native-validation` then runs the **full Maven suite, Python suite, and pinned SecondString differential on each of those five targets**. `validation` adds the Ubuntu lifecycle probe, benchmark smoke, internal-frame/inventory checks, and worker probes; the pinned Zingg contract/differential jobs run on Windows and Linux. Python also has a dedicated 3.10–3.14 matrix. Offline package assembly and no-system-Java/worker reliability checks run across the same five target families, with extra Docker/RSS/process-kill checks on Linux and the Windows bundle job. This table is the current support contract: compilation, tests, packaging and release evidence are separate gates; local Windows/WSL runs in `docs/validation-status.md` are not hosted-runner evidence.

| Target family | Compile | Full Maven/Python tests | Package assembly | Release evidence |
|---|---:|---:|---:|---:|
| Linux amd64 | yes | yes | yes, plus Docker/RSS/kill | pending hosted green run and security/license sign-off |
| Linux arm64 | yes | yes | yes | pending clean-host/release sign-off |
| macOS x86_64 | yes | yes | yes | pending clean-host/release sign-off |
| macOS arm64 | yes | yes | yes | pending clean-host/release sign-off |
| Windows x86_64 | yes | yes | yes, plus bundled-JRE/no-system-Java | pending hosted green run and signing |

Create a rollback artifact from a verified bundle with `./packaging/create-rollback-package.ps1 -Bundle dist/zingg-duckdb-0.1.0 -Output dist/zingg-duckdb-0.1.0-rollback.zip` on Windows, or `bash packaging/create-rollback-package.sh dist/zingg-duckdb-0.1.0 dist/zingg-duckdb-0.1.0-rollback.zip` on Linux/macOS/WSL. Verify either artifact with the matching `verify-rollback-package` script. Both front ends use the same Python-standard-library implementation, which validates the source bundle, creates a deterministic archive whose manifest binds the bundle `SHA256SUMS`, safely materializes verified in-bundle file links (such as repeated legal notices generated by `jlink`) as regular ZIP entries, rejects unsafe links/paths and corrupted payloads, and refuses to overwrite an existing output. The normal Windows and native POSIX package workflows create and verify the rollback artifact automatically.

The release policy is bundled as `config/release-policy.json`. A JRE build emits `runtime/java/JDK-PROVENANCE.json` with vendor, Java version/build, architecture, bundled executable SHA-256, and JDK `release` file SHA-256. It also emits `JDK-LEGAL-MANIFEST.json`, an exact inventory of legal resources from the actual `jlink` output (including safe, internal symlinks); package verification validates both manifests and all file contents. Windows and Linux/WSL packaging have been exercised with Microsoft OpenJDK 21.0.12.1 (45 legal resources) and Ubuntu OpenJDK 21.0.12.1 (44 resources), respectively. These local builds validate mechanics only: the release owner must still select/approve the production vendor/build and security-update policy, review the SPDX/legal inventory, reconcile all shipped artifacts, and Authenticode-sign `SHA256SUMS` with a timestamp.

The Windows bundle exposes `bin/zingg-duckdb.cmd` and `bin/zingg-duckdb.ps1`; both require and invoke only the bundled Java 21 runtime and worker jar.

The optional Native Image build has matching entry points: `./packaging/build-native-image.ps1` on Windows and `sh packaging/build-native-image.sh [native-image-path] [output-directory] [binary-name]` on Linux/macOS/WSL. Both require the reactor-built worker JAR and GraalVM Native Image running on **JDK 22 or later**; the wrappers fail closed on older or unknown JDKs because DuckDB no longer supports build-time driver initialization on JDK 21. They disable fallback images, generate a temporary target-specific reachability configuration (including only the current OS/architecture's DuckDB JNI library), and write a SHA-256 sidecar. `prepare_native_image_config.py` supports Linux x64/ARM64, macOS universal x64/ARM64, and Windows x64. The supported production distribution remains the bundled Java 21 JVM runtime; Native Image remains experimental and is not included in normal bundles until a JDK 22+ relocation and platform matrix passes. `python3 packaging/compare_native_image.py <binary> --warmups 1 --repetitions 5 --report <json>` compares protocol, SQL row counts, classifier training/artifact reload/MATCH outputs, startup-to-ping, process RSS, and artifact size against the JVM worker over paired fresh-process runs, checking functional equality each time and reporting raw samples plus robust summary statistics. Hosted reproducibility, workload/type/resource coverage, sustained performance, security/deserialization review, and platform-specific builds remain open.

Linux/macOS equivalents are available without PowerShell: `create-source-archive.sh`, `verify-source-archive.sh`, `generate-provenance.sh`, `generate-sbom.sh`, `verify-package.sh`, `verify-no-system-java.sh`, `verify-rss-linux.sh`, and `package-native.sh`. `package.sh` uses the native assembler automatically when `pwsh` is unavailable. Set `CREATE_JRE=true` when invoking `package-native.sh` to include a Java 21 `jlink` runtime. The native checksum path uses Python's standard library rather than GNU-only `sha256sum`/`find -printf`, so it is suitable for standard Linux and macOS shells.

## Windows/Linux command parity

The two entry points intentionally implement the same release contract:

| Release operation | Windows PowerShell | Linux/macOS/WSL POSIX shell |
|---|---|---|
| Assemble production bundle | `./packaging/package.ps1 -CreateJre` | `CREATE_JRE=true ./packaging/package.sh` or `bash packaging/package-native.sh` |
| Verify bundle and checksums | `./packaging/verify-package.ps1 -RequireJre` | `bash packaging/verify-package.sh <bundle> true` |
| Verify source archive | `./packaging/verify-source-archive.ps1` | `bash packaging/verify-source-archive.sh <archive>` |
| Check operation without system Java | `bin/zingg-duckdb.cmd` with a restricted `PATH` | `bash packaging/verify-no-system-java.sh <bundle>` |
| Measure Linux worker RSS | N/A (Windows has a separate CI launcher smoke) | `bash packaging/verify-rss-linux.sh <bundle>` |

The POSIX no-system-Java smoke uses only a restricted `PATH` and bundled Java, and avoids Linux-only `/proc`, `env -i`, and symlink assumptions so it can run on Linux, macOS, and WSL. RSS and process-group-kill probes are intentionally Linux-only. The Windows path is tested with the `.cmd` launcher under a restricted `PATH`. Local WSL/Windows results do not substitute for clean hosted macOS or ARM runner execution, which remains a release qualification task.

The dedicated `.github/workflows/security.yml` builds the native Linux release package, uploads its generated SPDX SBOM, and scans that exact SBOM with OSV-Scanner on pushes, pull requests, and weekly, without an NVD credential. It fails closed on scan errors and known vulnerabilities and archives the SARIF report. The reusable workflow is pinned to upstream commit `a345acffa64b0eaede81a3d9aae6141214d9c8fc` (OSV-Scanner Action v2.6.0). The separate OWASP Dependency-Check job in `build.yml` remains opt-in because it requires NVD access: set repository variable `ENABLE_SECURITY_SCAN=true` and secret `NVD_API_KEY` to run that additional scan. Neither automated scan constitutes license approval, native-binary review, vulnerability triage, or release sign-off.
