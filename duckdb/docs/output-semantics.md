# Output semantics

Graph output adds zero-scored implied pairs before entity min/max aggregation. Link output retains the released asymmetry: left-side projection is deduplicated while the right-side relation remains multiplicity-preserving. These operations are intentionally separate from connected-component discovery so that output compatibility does not alter graph topology.

File egress is selected by extension: CSV (`.csv`/default), Parquet (`.parquet`), JSON (`.json`/`.jsonl`), and Arrow IPC (`.arrow`/`.feather`). All writers execute on the owning DuckDB job connection through `COPY`, preserving the frame ownership and cleanup model.
Arrow IPC ingress is supported for `.arrow` and `.feather` inputs through the pinned Arrow Java runtime; unsupported complex fields are rejected with a typed diagnostic.

Pipeline file publication is serialized per destination after resolving the output parent directory to its real path (and applying case-insensitive local lock identity on Windows). An exact-key in-JVM lock registry reference-counts active/waiting users and removes idle entries, avoiding both unbounded lock-map growth and false serialization of unrelated destination paths. A persistent sibling `.<filename>.lock` sidecar coordinates cooperating processes with an OS file lock; the sidecar is intentionally retained because unlinking a lock file while another process has it open can split lock ownership across inodes. Under that lock, a retry removes only direct-child regular files matching `.<filename>.partial-*`, then writes a fresh sibling temporary file and atomically replaces the destination. A process hard-stopped before rename leaves the old destination intact and may leave a staging file until the next writer retries; that retry cleans the orphan before publication. A completed atomic rename is the commit point. Symlink lock targets fail closed, symlink staging candidates are never followed/deleted, and filesystems without atomic replacement fail closed. This is process-crash/retry recovery, not a guarantee against power loss, directory-entry loss, hostile non-cooperating writers, or lock semantics on every network filesystem.

The compatibility function surface includes the explicit `HashRegistry` (`java_hash`, `lower`, `trim`, `sha256`, `md5`, `length`, `java_round`) and `SimilarityRegistry` (`exact`, `jaccard`, `normalized_levenshtein`, `jaro`, `jaro_winkler`). Similarity results are constrained to the inclusive range `[0,1]`; the v0.7 `jaro_winkler` alias intentionally delegates to plain Jaro. Detailed registered and upstream feature status is maintained in the [semantic inventory](semantic-inventory.md); upstream MatchType names are not evidence that their feature generators are implemented locally.
